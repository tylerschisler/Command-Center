# Security Architecture — V1

## Security Goals
- local-first storage
- encrypted local database
- encrypted backups
- controlled cloud AI usage
- least-privilege Jarvis tools
- no hard-coded secrets
- no silent telemetry
- reliable recovery
- auditability of meaningful changes

## Threat Model
Primary risks:
- lost/stolen laptop
- accidental deletion
- database corruption
- over-permissioned AI actions
- cloud leakage through excessive context
- exposed API keys
- malicious/incorrect generated code
- backup failure
- unsafe destructive operations

## Local Database Encryption
The active SQLite database should be encrypted using a mature, maintainable mechanism compatible with the chosen runtime.

Requirements:
- encryption at rest
- no plaintext fallback in production
- key must not be committed to source control
- document key storage and recovery strategy

Implementation choice should be documented before production use.

### Phase 1.5 implementation
The active database uses SQLite3 Multiple Ciphers through the maintained `better-sqlite3-multiple-ciphers` build. Drizzle continues to use its official `better-sqlite3` adapter because the encrypted driver is API-compatible and is installed under that expected package name. Connections explicitly select the non-legacy sqleet ChaCha20-Poly1305 scheme, apply the key before any schema read, keep temporary SQLite storage in memory, and fail closed on plaintext files or invalid keys.

The database master key is 32 random bytes generated by Node's operating-system CSPRNG and stored as a generic secret in the user's macOS Keychain using native Security-framework bindings. Application code reads it only when opening, backing up, validating, restoring, or performing an explicit recovery operation, and clears its local buffers afterward where practical. It is not stored in `.env`, source control, logs, or in plaintext beside the database or in backups.

### Phase 1.6 recovery credential
Recovery initialization generates a separate 32-byte CSPRNG credential encoded as `CCREC1.<base64url>`. The application shows it once and does not retain it. The user must store it offline or in a trusted password manager, separately from the application data and backup archives.

The credential is processed with scrypt using a random 32-byte salt and production work factors `N=131072`, `r=8`, `p=1`. The derived 256-bit key wraps the database master key using AES-256-GCM with a random 96-bit nonce and authenticated, versioned KDF metadata. The stored `.ccrecovery` file contains only salt, nonce, parameters, authentication tag, and encrypted master-key bytes. Possession of that file without the credential does not reveal the database key.

Recovery from the active database unwraps the candidate key and requires a successful encrypted SQLite open and integrity check before recreating the Keychain entry. Recovery from a backup first extracts the protected envelope, unwraps the candidate key, authenticates the complete `CCBACKUP1` envelope, verifies its hash, opens its encrypted database image, and runs SQLite integrity checking before writing either recovery material or the Keychain entry. No recovery flow creates a plaintext SQLite image.

If both the Keychain item and recovery credential are lost, neither the active database nor backups are recoverable. If the protected recovery material is also lost but a recovery-enabled backup remains, the backup carries a copy of that protected material. Credential rotation rewraps the same database master key and invalidates the old credential for the active `.ccrecovery` file; older backups retain their historical envelope and therefore still require the credential that existed when each was created. Create a new backup immediately after rotation and retain old credentials while old backups are retained.

## Backup Encryption
All backups must be encrypted before being written to their destination.

Requirements:
- authenticated encryption
- versioned backup manifest
- schema version
- restore verification
- clear recovery process

Phase 1.5 backups use a versioned `CCBACKUP1` envelope. The source image is already ChaCha20-Poly1305 encrypted. A separate per-backup AES-256-GCM key is derived from the database master key using HKDF-SHA-256 and a random 32-byte salt. Each archive has a random 96-bit GCM nonce and authenticated metadata. Validation requires successful GCM authentication, a matching database hash and size, the correct database key, and a passing SQLite integrity check.

New Phase 1.6 backups include the cryptographically protected recovery envelope in authenticated metadata. They never include the recovery credential. Older valid `CCBACKUP1` files remain restorable when Keychain is available, but cannot recreate a missing Keychain entry.

Restore is intentionally destructive and requires explicit confirmation. The existing encrypted database is checkpointed and renamed to a uniquely named protected copy before the restored image is activated. If activation or integrity verification fails, the protected copy is put back. After successful activation and integrity verification, the application keeps no more than three `pre-restore` copies. Plaintext conversion likewise produces an encrypted `pre-encryption` rollback copy and retains no more than three after success. A protected copy is safe to delete once the active database is verified and a separately validated backup exists; Phase 1.6 bounded pruning prevents unlimited stale copies but is not a substitute for Phase 9 retention management.

## Secret Management
Never commit:
- OpenAI API key
- speech API keys
- news API keys
- encryption keys
- backup passphrases

Use:
- environment variables during development
- secure local secret storage for normal use when feasible

Provide `.env.example` without real secrets.

## Cloud AI
Cloud AI is allowed for V1.

Rules:
- only minimum necessary context is sent
- entire database is never sent by default
- user can disable cloud AI
- cloud AI should not be required for core CRUD functionality
- no sensitive data should be sent unless allowed by user configuration
- log enough metadata to understand AI usage, but do not create unnecessary sensitive logs

## Jarvis Permissions
Jarvis uses an explicit tool allowlist.

Read actions:
- generally allowed without confirmation

Low-risk writes:
- may execute with visible confirmation and undo where practical

High-impact/destructive actions:
- require explicit confirmation

Examples requiring confirmation:
- delete project
- delete many tasks
- bulk completion
- archive many records
- destructive restore
- large knowledge overwrite

Jarvis must not:
- execute arbitrary SQL
- run shell commands from natural-language user input
- read filesystem locations outside approved application paths
- modify source code at runtime
- access secrets directly unless required by provider code

## Activity Audit Trail
Meaningful application actions must create ActivityEvents.

Activity records should support:
- what happened
- what entity changed
- when
- source (manual, jarvis, voice, import, system)
- useful metadata

## Undo / Recovery
Provide undo or recovery for:
- low-risk Jarvis mutations
- batch actions where feasible
- accidental edits through version history
- knowledge changes through KnowledgeVersion
- major operations through restore points

## Backup Policy
Default:
- daily backups
- retain 14 daily
- retain 8 weekly
- retain 12 monthly

Backup should run when:
- app starts and required backup is overdue
- user manually requests backup
- before defined high-risk operations when practical

Phase 1.5/1.6 established manual create, validate, restore, and portable Keychain recovery. Phase 9 adds startup-driven daily checks, daily/weekly/monthly retention tiers, optional secondary folders, restore points, and the backup-management UI while preserving the same encrypted archive and recovery boundaries.

## Restore Testing
Automated test must:
1. create known data
2. back it up
3. remove/corrupt test database
4. restore backup
5. verify recovered data
6. fail loudly if verification differs

## Dependencies
- prefer widely used, maintained dependencies
- avoid unnecessary packages
- pin versions appropriately
- run dependency vulnerability checks before release checkpoints
- document security-sensitive libraries

## Logging
Do not log:

- encryption keys
- raw authentication material

Be careful logging:
- full AI prompts

Internet use is expected for:

## Phase 7 AI Boundary

Cloud AI is disabled by default. Enabling it is an explicit local setting and does not affect local CRUD, search, briefings, encryption, backup, or recovery. `OPENAI_API_KEY` and `OPENAI_MODEL` are server-only environment values; settings reveal only configured/not-configured status.

Jarvis sends a user prompt plus only context selected through allowlisted tools or the explicitly open Project/Knowledge record. Retrieved notes and Knowledge content are wrapped and labeled as untrusted application data and may never redefine system policy or tool permissions. Tool names and arguments are independently allowlisted and schema-validated; prompt instructions cannot create new capabilities. Structured provider output is validated and rendered without executable HTML.

The OpenAI request uses `store: false`. Command Center does not persist prompts, responses, or conversational history. Encrypted `ai_usage_records` contain provider, model, timestamp, request/token counts, and an optional future cost field only. Application logs must not contain prompts, responses, API keys, database keys, recovery credentials, tool payloads, full Knowledge content, or backup material.

## Phase 8 Speech Boundary

Microphone access is browser-only and begins solely after an explicit pointer press or focused Space/Enter press on the push-to-talk control. Capture ends on release and is force-stopped after 30 seconds. Command Center does not request background microphone access, detect wake words, record continuously, or open a Realtime session.

The browser sends audio to a local server route over multipart form data. The route accepts only WebM, MP4/M4A, MP3, WAV, or Ogg audio, rejects unexpected fields, limits the recording to 5 MB and 30 seconds, and generates its own safe provider filename. Audio remains in memory and is discarded after the request. It is never written to SQLite, application logs, temporary files, encrypted backups, or usage records. Transcripts are short-lived request/browser state and are not persisted or logged.

OpenAI speech calls reuse the Phase 7 server-only API-key boundary. Speech failure logs contain only provider, model, stage, HTTP status, provider error type/code, and request ID. They exclude audio, transcripts, prompts, tool payloads, model output, and secrets. STT failure preserves typed/manual workflows; TTS failure cannot invalidate an already completed Jarvis action.

Voice settings and aggregate usage metadata live inside encrypted SQLite. Usage records contain no raw audio or transcript. `OPENAI_STT_MODEL`, `OPENAI_TTS_MODEL`, and `OPENAI_TTS_VOICE` are server-only environment values without a `NEXT_PUBLIC_` prefix. Estimated speech cost remains null until reliable configurable pricing is introduced; Phase 9 may add cost cutoffs without changing this data-minimizing boundary.

## Phase 9 Hardening

Public Intelligence feeds are an explicit network boundary. Defaults are reviewed government feeds and configuration accepts at most 20 public HTTP(S) RSS/Atom URLs. Literal localhost, private-network, file, data, and JavaScript URLs are rejected. Retrieved HTML is never rendered; scripts/styles/tags are stripped and bounded structured text is stored. Article text is never allowed to invoke Jarvis tools, alter permissions, or trigger a write. Save to Knowledge is an explicit user action.

Automatic and secondary backups retain `CCBACKUP1` authenticated encryption. The secondary destination receives no plaintext. Restore requires archive validation and typed confirmation, protects the active encrypted database first, verifies activation, and rolls back on failure. Cleanup requires configured-root containment and managed filenames; unrelated files and failed-validation artifacts are not deleted.

Usage estimates contain no prompts, responses, audio, or Knowledge content. Budget enforcement is optional and applies only to cloud AI/speech. Unknown pricing remains unknown. Pricing configuration is versioned separately from service logic.

The V1 secret scan rejects tracked `.env`, database, backup, recovery, private-key, OpenAI-key, and portable-recovery credential material. Logger redaction covers sensitive context keys and recognizable secret values. Network/provider logs remain limited to safe status, request ID, provider/model, stage, and error metadata.

The dependency audit on 2026-10-14 found zero production/runtime vulnerabilities. Nine advisory paths (five high, four moderate) remain in development-only tooling: the Next ESLint glob chain and Drizzle Kit's legacy esbuild loader. Next and its matching ESLint configuration were updated to 16.4.1. npm currently offers only breaking/downgrade suggestions that do not remove the affected maintained dependency paths; forced fixes were intentionally deferred. Development servers must remain bound to localhost and untrusted glob patterns must not be accepted from network input.

## V1.1 permanent deletion

Permanent deletion requires an explicit typed confirmation in both the UI and service method; API callers cannot bypass the service check. Each repository executes relationship cleanup, domain deletion, and the deletion ActivityEvent atomically. Events retain entity type/ID and a generic action description but omit deleted titles, notes, page content, and other sensitive fields. Project deletion detaches rather than cascades domain work. Person deletion fails while any Task or Request assignment remains, including completed or archived records. Knowledge versions, taxonomy joins, relationships, and FTS entries are removed transactionally. These operations never inspect or modify encrypted backups, protected pre-restore copies, Keychain state, or recovery material; previously created backups may still contain the deleted historical record until normal encrypted retention expires.
